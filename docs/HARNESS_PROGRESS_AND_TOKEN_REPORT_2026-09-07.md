**유지할 정책과 실제 비용**

현재 정책은 조사·명세 작성에는 빈 PLAN/TASK를 요구하지 않고, 명시적인 정책 문서 작업에는 초기화를 요구하지 않는다. 일반 단일 작성자는 기본 모드에서 claim을 만들지 않으며, 결과·리뷰 기록도 필요한 목적이 있을 때 사용한다. 이 부분은 이미 적용된 효율화이므로 새 개선 성과로 중복 계산하면 안 된다.

현재 PLAN의 fingerprint에 결합된 실제 소유자 결정, TASK 연결, 결정 적용, 실행 게이트는 유지해야 한다. 변경 중인 사용자 파일 보호와 구현·정적 검증·통합 검증·브라우저 검증·실환경 검증·고객 수락의 구분도 적절하다. 고위험 작업의 암호학적 인간 승인을 토큰 절약 대상으로 삼을 이유는 없다.

다만 일반적인 작은 수정에도 요구사항·기능·완료 기준·PLAN/TASK의 추적 관계와 승인 절차가 필요하므로 고정 비용은 존재한다. 승인된 TASK 범위 안의 반복 구현까지 매번 새 승인으로 해석하지 않고, 검토할 수 있는 하나의 변경 묶음으로 계획하는 것이 중요하다. 범위가 바뀌면 새 결정이 필요하다는 원칙은 그대로 유지한다.

**토큰 효율: 이번에 측정한 것**

UTF-8 텍스트를 읽어 CRLF를 LF로 통일한 문자 수를 계산했다. 아래 HEAD 대비 차이는 이번 요청 이전부터 존재하던 작업 트리 변경의 차이다. 이번 보고서가 정책을 줄였다는 의미가 아니다. 모델 usage metadata와 tokenizer는 사용하지 않았으므로 실제 입력·출력·캐시 토큰 및 금전 비용은 미측정이다.

|---|---:|---:|---:|
| `AGENTS.md` | 7,191 | 6,295 | −12.5% |
| Codex 시작 구성: AGENTS + CODEX_START_PROMPT | 7,410 | 6,492 | −12.4% |

마지막 행은 AGENTS·두 시작 프롬프트·CLAUDE·README 5개와 기존 추적 docs 문서 12개를 합산했다. 미추적 `POLICY_REVIEW.md` 4,235자를 더하면 보고서 작성 전 문서 18개의 합계는 143,496자다. 새로 작성한 이 보고서는 비교에서 제외했다.

시작 구성은 후보 문서 묶음의 크기이며 특정 앱이 실제로 주입한 payload의 측정값은 아니다. 사용자 메시지로 이미 받은 정책도 모델 문맥의 일부이므로 파일을 다시 읽지 않았다는 이유로 0토큰으로 세면 안 된다. 반대로 사용하지 않는 다른 에이전트의 adapter까지 시작 비용에 넣을 필요도 없다.

현재 정책의 거친 `문자 수 / 4` 방식으로 Codex 시작 구성은 약 1,623, Claude는 약 1,662 토큰 상당이다. 실제 토큰 수는 아니다. PLAN/TASK·handoff·`next` 출력을 더하기 전부터 재개 세션 목표 1,500에 근접하거나 이를 넘는 추정치이므로, 목표 달성을 선언할 수 없다. 실제 tokenizer나 adapter usage로 확인해야 한다.

시작 정책이 짧아지는 동안 상세 문서가 길어진 것은 그 자체로 실패가 아니다. 상세 문서를 매 세션 읽는지, 필요한 부분만 읽는지가 모델 입력량을 결정한다. 모든 문서를 반복 로딩하면 시작 문서를 줄인 효과가 쉽게 상쇄된다. 이 보고서도 조사 산출물로 보관하고 일반 시작 문맥에 자동 추가하지 않는 편이 좋다.

**기계 단계 수와 ‘5단계’ 목표**

[현재 운영 절차](WORKFLOW.md#the-path-as-it-runs-today)를 기준으로, 요구사항·기능·PLAN/TASK 내용 작성이 끝났고 아직 sync 전이며 project lifecycle은 DISCOVERY인 경우를 계산했다. 초기화·내용 작성·실패 재시도는 제외한 구조적 산정이다. 실제 수행 시간을 측정한 결과는 아니다.

| 구간 | 명령 또는 편집 횟수 |
|---|---:|
| `plan sync` | 1 |
| 결정 전 `validate --strict` + `report decision-package` | 2 |
| 실제 소유자 결정 후 `approval confirm` | 1 |
| `state.json`의 두 PLAN 포인터를 한 번에 편집 | 1 |
| SPECIFYING → PLANNING → DECISION_READY 전환 | 3 |
| `plan apply-decision` | 1 |
| TASK를 READY로 전환 | 1 |
| 실행 전 strict 검증 + TASK gate | 2 |
| 하네스 명령·편집 소계 | **12** |

소유자 결정은 별도로 1회다. 해당 구간의 Git 상태 확인도 기계 단계로 포함하면 13회 이상이다. 추가 진단·상태 확인·재시도가 있으면 늘어난다. 여러 명령을 한 shell 호출에 넣어도 같은 기준에서는 단계 수가 줄지 않는다.

초기 포인터 편집 1회와 lifecycle 전환 3회를 제거해도 위 조건에서는 하네스 단계가 8회 남는다. 따라서 [효율 정책](CONTEXT_EFFICIENCY.md)의 5단계 목표는 알려진 오류 수정만으로 자동 달성되지 않는다. 작성·preflight·상태 적용·검증을 안전하게 통합하는 CLI 설계가 더 필요하다. Git 확인과 내부 검사를 어떻게 집계했는지도 전후 비교에서 동일하게 공개해야 한다.

**바로 적용할 운영 방법과 추가 개발 제안**

| 순서 | 방법 | 현재 적용 가능 여부 | 효과를 확인할 지표 |
|---|---|---|---|
| 1 | 이미 제공된 정책은 재사용하고 `next` 뒤 필요한 PLAN/TASK·문서 절만 읽는다. README·전체 status·전체 schema는 조사할 이유가 있을 때 확장한다. | 현재 정책에 이미 허용·명시됨 | 변경 없는 파일의 반복 읽기 비율, 첫 실행 가능 안내까지 입력량 |
| 2 | 경로·기호를 `rg`로 찾은 뒤 해당 범위를 읽는다. 독립적인 읽기는 묶되 총 출력 예산을 나누고 truncation 발생 시 필요한 부분만 보충한다. | 현재 도구로 가능 | tool-output 문자 수, 잘린 출력 수, 재조회 횟수 |
| 3 | `doctor`·strict·게이트를 정책상 필요한 경계에 실행한다. 무변경 조사 턴에서 같은 진단을 되풀이하지 않고, 기록·범위·권한 등이 바뀌면 필요한 검사를 새로 한다. | 현재 정책에 이미 명시됨 | 같은 상태에 대한 반복 명령 수, 검사 누락 여부 |
| 4 | decision package가 반환한 현재 fingerprint를 재사용하고 범위·위험·조건·미해결 사항·권고를 한 번에 제시한다. 동일 결정으로 런타임 오류를 해결하려고 재질문하지 않는다. | 현재 기능으로 가능 | 소유자 결정 턴 수, 중복 fingerprint 조회 수 |
| 5 | 작업 재개 요약에는 현재 승인 참조·fingerprint·작성 범위·dirty 소유권·정확한 실패·미검증 항목·다음 행동을 담는다. 실행 재개 시 현재 기록과 필수 검사를 확인한다. | 서면 요약으로 가능; 공식 HOF/RES 제약은 별도 | 재개 시 읽은 파일 수와 재탐색량, stale 정보 사용 여부 |
| 6 | R1~R6과 R9를 함께 해결하여 일반 승인·재승인·다음 PLAN 경로를 끝까지 연결한다. | 승인된 런타임 PLAN/TASK 필요 | 수동 상태 편집 0회, 불필요한 승인 재요청 0회, 전체 경로 strict와 gate 통과 |
| 7 | 필수 내용 작성 옵션과 간결한 진단 출력을 추가한다. 출력은 차단 사유와 근거 위치를 먼저 보여 주고 상세 결과는 요청 시 확장하되 실패를 생략하지 않는다. | 승인된 CLI 구현 필요 | 초기 작성 오류, preflight 실패 후 수정 횟수, 출력량 |
| 8 | 변경 없는 문서의 path/hash·읽은 절을 기억하는 문맥 목록과 usage 집계를 지원한다. 이를 승인·검증 캐시로 사용하지 않는다. | 세션 내 추적은 가능; 지속 자동화는 별도 구현 | 반복 입력량, 입력·출력·캐시 토큰, 잘못된 재사용 건수 |
| 9 | 정상 경로가 안정된 뒤 leaf PLAN 승인을 구현하고, 여러 승인 대상을 한 번에 검토할 수 있는 결정 패키지를 설계한다. 각 승인 대상과 fingerprint는 계속 구분한다. | `harness.plan/v2` 구현 필요 | 무관한 TASK까지 중단되는 횟수, 변경 후 재개 비용 |

원문 문서·출처는 보존하면서 모델이 읽는 부분을 줄여야 한다. 요약만 남기고 승인 조건이나 실패를 삭제하면 재작업과 판단 오류 비용이 늘어난다. 캐시된 입력은 총입력·비용과 별도로 측정하며, 캐시가 있다는 이유로 입력이 무료라고 가정하지 않는다.

Markdown 전환은 읽기·편집 경험을 개선할 수 있지만, 같은 구조와 내용을 유지한다면 확장자 변경만으로 토큰이 줄어든다고 볼 수 없다. 전체 기록 형식 변경(`docs/RECORD_FORMAT.md`, 삭제됨)은 승인 경로의 결함을 해결한 뒤 별도 이유와 측정으로 평가하는 것이 적절하다. 미구현 `--parent`, `active_plans`, 기록 변환 명령을 현재 운영에 사용하면 안 된다.

**권고하는 작업 묶음과 완료 기준**

| 작업 묶음 | 범위 | 완료 판단 기준 |
|---|---|---|
| A. 정상 진행 경로 완성 | 문제 목록 1~5·7·8·10, 정확한 next, 필수 작성 옵션, CLI 전 구간 검증 | 새 프로젝트 → 최초 승인 → TASK 실행 준비 → TASK 추가·재승인 → 기존/새 TASK 검사 → PLAN 종료·다음 PLAN 전환을 수동 state 편집 없이 진행. 각 실행 경계에서 strict와 gate가 모두 통과하고 과거 승인은 보존된다. |
| B. 일상 문맥 비용 관리 | 범위별 읽기, 반복 실패 보존, 진단 출력 축소, usage 집계 | 동일 작업의 전후 입력·출력·캐시 토큰과 재조회·재시도 감소를 관측하고, 승인·dirty·차단·검증 검사 누락은 없어야 한다. |
| C. 공식 단일 작성자 기록과 복수 작업 흐름 | 문제 목록 9, 이후 leaf PLAN 승인 | 공식 결과·인수인계의 실제 소유권과 검증 계보를 유지하고, 관련 없는 leaf의 승인 유효성이 유지되는지 검증한다. |

작업 A의 인수 기준에는 정상 성공뿐 아니라 오래된 fingerprint, 조건 미충족, 빈 구현 write scope, 미완료 PLAN 교체, 실패·누락된 검증의 거부 사례도 포함해야 한다. 테스트용 결정은 격리된 fixture에서만 사용하고 실제 프로젝트의 소유자 승인으로 취급하지 않는다. 하네스 런타임 변경의 릴리스 검증에는 정책대로 `python scripts/check_repo.py full --self-test`가 필요하다.

현재 checkout은 미초기화 상태이므로 위 구현을 시작하려면 필요한 기록 작성과 preflight를 먼저 완료하고 실제 소유자 결정·적용·TASK gate를 갖춰야 한다. 이 보고서 작성에는 그 절차가 필요하지 않다. 이번 요청에서 구현 승인을 요구하거나 승인 기록을 만들지는 않았다.

**효율 개선을 검증할 방법**

읽기 전용 조사, 작은 수정, 중간 기능 변경, 동시 작업, 고위험 준비를 분리하고 새 세션과 재개 세션도 나눈다. 첫 비교는 동일 snapshot·작업 범위·모델 조건에서 시나리오별 여러 번 수행해 중앙값과 최악 사례를 기록한다. 차단된 실행을 통계에서 빼면 개선 효과가 과장된다.

| 지표 | 수집할 값과 해석 |
|---|---|
| 시작 비용 | 하네스 정책·adapter·필수 문맥·첫 실행 가능한 안내까지의 tool output. 전체 모델 요청 입력량은 별도로 기록한다. |
| 작업 전체 비용 | adapter가 제공하는 실제 input/output/cached usage와 전체 작업량. 모델 수치가 없으면 문자 수만 확정값으로 제시한다. |
| 반복 비율 | 변경 없는 hash의 반복 로딩량 / 전체 입력량. 파일 읽기뿐 아니라 주입된 중복 정책도 고려한다. |
| 거버넌스 비율 | 첫 구현 편집 전 거버넌스 토큰 / 전체 작업 토큰. 작은 수정의 고정 비용을 중간 기능의 25% 목표와 혼합하지 않는다. |
| 진행 비용 | 내용 작성 완료부터 strict·TASK gate 통과까지 CLI 횟수, 수동 기록 편집, 소유자 결정 턴, 실패 복구량. shell 묶음과 내부 검사 수도 구분한다. |
| 정확성 | 범위 초과, stale 승인 사용, dirty 침범, 실패를 PASS로 표현한 횟수. 비용 절감과 함께 판단한다. |

현행 목표인 재개 시작 1,500 입력 토큰, 소유자 결정 1회·기계 단계 5회, 중간 변경의 거버넌스 비율 25% 이하, 반복 비율 10% 이하는 목표값으로 유지하되 아직 달성했다고 표현하지 않는다. 원문 프롬프트·고객 데이터·자격 증명·보호된 승인 자료는 측정 로그에 넣지 않는다.

**이번 보고서의 확인 범위**

현재 상태, 문서 크기, 주요 런타임 분기와 관련 테스트 준비 코드를 확인했다. 게시할 보고서의 로컬 링크 23개와 참조 위치, 코드 블록 구조·공백 검사를 통과했다. 기존 변경 파일 22개는 검사 시 SHA-256이 모두 동일했고, 이번에 추가한 변경 경로는 이 보고서 하나다. 기존 diff와 새 보고서의 공백 검사도 통과했다.

런타임 결함을 고치거나 제품 테스트를 실행한 결과가 아니므로 `INTEGRATION_VERIFIED`, `BROWSER_VERIFIED`, `LIVE_ENV_VERIFIED`, `CUSTOMER_ACCEPTED`, `CLOSED`를 주장하지 않는다. 최초 정책 검토에서는 `doctor`, `validate --strict`, `check_repo.py full`을 실행하지 않았다.

후속 게시 준비에서 `python scripts/check_repo.py full`을 실행했다. 컴파일은 PASS, `tests-full`은 제품 테스트 모듈이 없어 SKIPPED, `harness-strict`는 프로젝트 기록이 없어 SKIPPED였다. wrapper 종료 코드 0은 생략된 검증의 PASS를 뜻하지 않는다. 하네스 자체 테스트는 실행하지 않았고, 문서 게시를 위해 프로젝트를 초기화하지 않았다.

의사결정 권고는 **정상 승인·재승인·PLAN 교체 경로를 먼저 완성하고, 같은 사용 시나리오에서 반복 문맥과 실패 복구 비용이 줄었는지 측정하는 것**이다. 정책의 통제 기준을 보존하면서 프로젝트 진행과 토큰 효율을 함께 개선할 수 있는 우선순위다.
