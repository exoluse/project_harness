# Project Agent Harness

**고객 문서·프롬프트·기존 코드를 바탕으로 프로젝트의 요구사항, 설계, 계획, 구현과 검증을 관리하는 하네스입니다.**
사용자는 원하는 결과와 진행 범위, 실제 결정을 전달하고, 에이전트는 필요한 분석·기록·작업을 수행합니다.
하네스 하나는 자신이 들어 있는 프로젝트 저장소 하나를 관리합니다.

새 프로젝트를 시작하거나, 진행 중인 프로젝트를 인수하거나, 코드에서 요구사항과 설계를 복원하는 데 사용할 수 있습니다.
단계별 입력·산출물·완료 기준을 갖춘 **Waterfall 개발 구조**를 따르며, 진행 중에도 **Agile 방식으로 요구사항과 결과물을 수정**할 수 있습니다.
순차 개발과 반복 개발을 모두 지원하고, 스프린트는 필수가 아닙니다.

이 README는 사용자용 안내입니다. 공통 정책의 기준은 [AGENTS.md](AGENTS.md)이며, 상세 절차와 현재 구현의 한계는 아래 연결 문서에서 확인합니다.

## 시작하기

Python 3와 Git을 실행할 수 있는 환경에서 코딩 에이전트로 프로젝트 폴더를 엽니다.
사용자가 내부 기록 형식이나 승인 명령을 직접 다룰 필요는 없습니다.
자료 위치, 원하는 결과, 이번에 어디까지 진행할지를 알려주세요.

| 상황 | 시작 방법 |
|---|---|
| 새 프로젝트 | 이 하네스 저장소를 새 프로젝트 폴더로 복제하거나 복사합니다. 숨김 폴더인 `.harness/`도 포함하고, 고객 문서와 목표를 전달합니다. |
| 진행 중인 프로젝트 | 먼저 기존 코드·문서·Git 변경 상태와 에이전트 정책·스크립트·CI의 충돌을 조사합니다. 도입 범위를 정하고 필요한 통합 작업의 권한을 갖춘 뒤 하네스를 적용합니다. 기존 파일 위에 일괄 덮어쓰지 않습니다. |
| 코드 분석만 필요 | 코드 저장소나 스냅샷과 분석 범위를 전달합니다. 외부 코드는 분석 입력이며, 자료를 제공했다는 이유로 그 저장소에 대한 수정 권한이 생기지는 않습니다. |
| 하네스 정책만 수정 | 수정할 정책 범위를 설명합니다. 정책 문서 편집을 위해 프로젝트를 초기화하거나 PLAN/TASK를 만들지 않습니다. |

새 프로젝트에서는 다음과 같이 요청할 수 있습니다.

```text
이 저장소의 AGENTS.md를 따라 프로젝트를 시작해줘.
고객 요구사항은 [문서 경로]에 있어.
먼저 요구사항과 완료 기준, 확인할 질문까지만 정리해줘.
```

기존 프로젝트에서는 다음과 같이 시작할 수 있습니다.

```text
이 프로젝트의 [분석 범위]를 인수하기 위해 현재 상태를 조사해줘.
기준 버전과 미커밋 변경을 구분하고, 코드·테스트·기존 문서를 근거로
현재 구현의 요구사항과 설계를 복원해줘.
사실·추론·미확인 사항을 나누어 분석 결과와 명세 기록까지만 작성해줘.
```

에이전트는 현재 공통 정책과 해당 도구의 어댑터를 읽고 `python scripts/harness.py next`로 시작합니다.
프로젝트 등록에 필요한 경우에만 초기화하고, 상태 확인이나 정책 검토 요청에서는 초기화하지 않습니다.
에이전트별 시작 안내는 [Codex](CODEX_START_PROMPT.md), [Claude Code](CLAUDE_START_PROMPT.md)와 [Claude 어댑터](CLAUDE.md)를 참고하세요.

## 요청 범위와 역할

| 하고 싶은 일 | 요청 예시 |
|---|---|
| 요구사항 정리 | “첨부 자료의 요구사항과 완료 기준을 정리해줘.” |
| 설계 | “이 요구사항에 맞는 구조, 데이터 모델, 인터페이스를 설계해줘.” |
| 역공학 | “현재 코드에서 요구사항과 설계를 복원하고, 근거와 불확실성을 표시해줘.” |
| 계획 작성 | “남은 작업, 순서, 의존성, 검증 방법까지 계획만 작성해줘.” |
| 구현·검증 | “이 범위의 구현과 검증을 진행할 수 있도록 구체적인 실행안을 준비해줘.” |
| 변경 검토 | “품절 표시 기능을 추가하고 싶어. 가능성, 영향, 필요한 작업을 검토해줘.” |
| 상태 확인 | “끝난 일, 남은 일, 막힌 이유와 검증하지 못한 부분을 알려줘.” |
| 전체 진행 | “요구사항부터 전달까지 진행해줘. 필요한 결정은 구체적인 범위를 준비해 설명해줘.” |

요구사항·설계·계획·검증 등 특정 단계만 요청하면 그 단계의 결과와 한계를 보고하고 멈춥니다.
전체 진행을 요청하면 준비된 단계를 현재 권한 안에서 이어가며, 필수 정보·결정이나 실제 차단 사유가 있을 때 확인합니다.

| 주체 | 책임 |
|---|---|
| 사용자·프로젝트 소유자 | 자료와 목표를 제공하고, 범위·우선순위·중요한 변경과 구체적인 실행안을 결정합니다. |
| 에이전트 | 자료와 코드를 분석하고, 명세·계획·기록을 작성하며, 실제 결정을 기록·적용하고 허용된 작업과 검증을 수행합니다. |
| 하네스 런타임 | 기록, 승인 범위, 의존성, 작업 점유와 검증 근거를 검사합니다. 검사 통과가 사용자 동의를 만들어내지는 않습니다. |
| 고객·권한 있는 서명자·운영 담당자 | 각자의 권한에 따라 최종 고객 인수, 고위험 승인 서명, 보호된 환경에서의 운영 작업을 수행합니다. |

프로젝트 소유자의 실행 결정과 고객의 최종 인수는 구분합니다.
에이전트가 결정을 기록할 수는 있지만, 사용자의 결정을 만들어내거나 인간 서명을 대신할 수는 없습니다.

## 개발 단계와 완료 기준

```text
조사·타당성 → 요구사항 → 설계 → 계획 작성 → 실행 준비
           → 구현 → 검증 → 고객 인수 → 배포·전달 → 인계·종료
                                                      → 유지보수
```

| 단계 | 주요 산출물과 다음 작업의 기준 |
|---|---|
| 조사·타당성 | 목표, 사용자, 포함·제외 범위, 제약, 가능성과 미확인 사항을 정리합니다. |
| 요구사항 | 기능·품질·데이터·운영 요구와 확인 가능한 완료 기준을 출처에 연결합니다. |
| 설계 | 구성 요소, 화면·흐름, 데이터·인터페이스, 예외 처리와 기술 선택을 구체화합니다. |
| 계획 작성 | 작업, 순서, 의존성, 수정 범위, 일정·위험·검증 방법을 작성하고 필수 계획 점검을 통과합니다. |
| 실행 준비 | 준비한 범위에 대한 실제 소유자 결정이 기록·적용되고, 시작할 TASK의 실행 게이트가 통과합니다. |
| 구현 | 승인된 범위의 결과물을 만들고, 편차·결함·미완성 부분을 기록합니다. |
| 검증 | 해당 버전과 완료 기준에 맞는 검사를 수행하고, 결과·근거·한계를 남깁니다. |
| 고객 인수 | 해당하는 계약상 인수 기준과 최종 고객 인수 승인 요건을 충족합니다. |
| 배포·전달 | 대상 버전·환경·전달 방법·복구 준비를 확인하고, 필요한 승인과 전달 후 검사를 갖춥니다. |
| 인계·종료·유지보수 | 전달, 인계, 유지보수 준비와 남은 의무를 확인합니다. 이후 변경도 같은 영향 분석과 검증 절차를 따릅니다. |

**계획 작성 완료와 실행 준비 완료는 별개입니다.**
계획만 요청한 경우 필수 계획 점검과 결과 보고로 끝나며, 실행 승인을 계획 완료 조건으로 요구하지 않습니다.
필수 점검이 실패하면 초안 또는 보완 필요로 보고합니다.
단계 준비 상태의 확인 자체가 매번 별도의 인간 승인을 뜻하지도 않습니다.

요구사항과 설계는 구현·검증·전달 이후에도 바뀔 수 있습니다.
영향받는 범위의 가장 앞선 단계부터 기준과 후속 작업을 갱신하고, 관련 실행 권한과 검증을 다시 확인합니다.
단계 설명은 임의의 런타임 상태 변경이나 프로젝트 초기화를 허용하지 않습니다.

[개발 방법](docs/DEVELOPMENT_METHOD.md)에서 상세 기준을, [HTML 진행 안내](docs/HARNESS_POLICY_REPORT.html)에서 전체 순서를 확인할 수 있습니다.

## 기존 프로젝트 인수와 역공학

이미 진행된 개발을 보존하면서 도입 시점의 기준을 세우고, 이후 관리할 범위를 정합니다.
하네스 초기 상태인 `DISCOVERY`는 인수를 위한 조사의 시작을 뜻하며, 기존 프로젝트의 실제 진도를 처음으로 되돌린다는 뜻이 아닙니다.

1. **분석 기준을 식별합니다.** 커밋과 미커밋 변경, 또는 스냅샷의 파일 해시를 기록하고 분석 범위·제외 영역·개발 및 배포 이력을 구분합니다.
2. **코드와 관련 자료를 함께 읽습니다.** 테스트, 설정, 기존 요구사항·설계·결정 문서를 대조하고 중요한 발견에 버전과 파일·심벌 등의 근거를 연결합니다.
3. **현재 구현의 요구사항과 설계를 복원합니다.** 구현 사실, 추론한 의도, 충돌과 미확인 사항을 구분합니다.
4. **현재 구현과 목표를 비교합니다.** 누락된 요구, 결함 의심 지점, 불충분한 검증과 사용자 확인 사항을 정리합니다.
5. **실제 남은 작업을 계획합니다.** 요청한 범위에 따라 문서 보완·검증·변경을 PLAN/TASK로 구성하고 해당 단계에서 마칩니다.

| 구분 | 문서에 담을 내용 |
|---|---|
| 현재 구현 | 코드에서 확인한 기능, 업무 규칙, 구조, 데이터와 인터페이스 |
| 추론·미확인 | 원래 목적이나 설계 이유에 대한 추론, 누락 자료, 서로 다른 자료의 충돌 |
| 목표 요구사항·설계 | 앞으로 달성할 동작과 제약, 합의된 내용과 아직 제안인 내용 |
| 후속 계획 | 현재 상태와 목표의 차이를 해소할 실제 작업, 의존성과 검증 방법 |

코드는 현재 구현의 근거입니다. 버그·임시 처리·테스트의 기대값을 곧바로 승인된 요구사항으로 취급하지 않습니다.
테스트 코드를 읽었다는 사실은 테스트 통과를, 배포 설정이나 과거 보고서는 현재 운영 환경의 정상 동작을 증명하지 않습니다.

과거 결정·테스트·배포 자료는 원래 버전의 이력으로 보존합니다.
현재 주장에 재사용할 때는 기준·버전·의존성·검증 대상과의 적용 가능성을 확인하며, 기존 승인·증거 게이트도 충족해야 합니다.
과거 작업을 하네스에서 수행한 것처럼 PLAN/TASK 실행, 승인, PASS를 소급 생성하지 않습니다.

문서 복원은 요청한 범위의 출처 연결, 현재·목표 구분, 누락·모순·질문을 보고하고 해당하는 필수 점검을 통과해야 완료로 판단합니다.
문서화 완료만으로 제품 검증이나 고객 인수를 주장하지 않습니다.
현재는 에이전트가 분석하고 기존 기록으로 연결하는 절차이며, 코드를 자동으로 가져와 문서와 진도를 변환하는 전용 기능은 없습니다.

상세 내용은 [인수·역공학 기준](docs/DEVELOPMENT_METHOD.md#existing-project-intake-and-reverse-engineering)과 [인수 절차](docs/WORKFLOW.md#existing-project-intake-and-reverse-engineering)에 있습니다.

## 실행 승인과 변경 관리

사용자의 요청은 인수·조사·명세·계획과 그 기록 작성을 허용합니다.
제품 코드 수정, 제품 테스트, 로컬 납품 문서 편집, 포맷팅, 커밋·fetch·충돌 해결·일반 push는 실행 경계를 따릅니다.
분석 결과와 명세 기록을 작성하는 권한이 로컬 제품 문서를 직접 수정하는 권한으로 확대되지는 않습니다.

일반 실행은 다음 순서로 준비합니다.

1. 에이전트가 가능성, 대안, 범위, 영향, 위험, 미확인 사항과 검증 방법을 구체화하고 PLAN/TASK를 연결합니다.
2. 필수 사전 점검을 통과한 뒤 명시적인 실행 범위와 그 버전 지문을 준비해 소유자에게 설명합니다.
3. 소유자가 제시된 범위에 “이 범위로 진행해”처럼 응답하면, 에이전트가 실제 메시지를 승인 기록으로 남기고 적용합니다.
4. 시작할 TASK의 게이트가 통과하면 해당 범위의 작업을 수행합니다.

사용자는 특별한 승인 문구나 지문을 입력하거나 명령을 실행할 필요가 없습니다.
다만 단순 변경 요청, 추가 자료, 침묵은 구체적인 실행안에 대한 승인으로 간주하지 않습니다.
이미 승인된 동일 범위에 대해 PLAN 승인, TASK 승인, 테스트 허가라는 이름으로 같은 결정을 반복해서 묻지 않습니다.

**결정의 단위는 검토한 실행 범위입니다.**
명시적으로 준비한 범위 안에서는 여러 단일 수준 PLAN이 같은 결정을 공유하고, TASK를 나누거나 실행 가능한 순서를 조정할 수 있습니다.
각 PLAN에 대한 결정 적용과 개별 TASK 게이트는 계속 필요합니다.
결과·수용 기준·수정 경로·기능·위험·일정 약속 등 중요한 조건이 승인 범위를 벗어나면, 그 차이와 영향을 준비해 한 번 새 결정을 받습니다.

기존의 정확한 지문에 결합된 승인은 원래 규칙을 유지합니다.
작업 구성이 바뀌면 PLAN 전체가 실행 불가 상태가 될 수 있으며, 이를 더 넓은 공유 승인으로 자동 변환하지 않습니다.
어느 방식이든 새 버전이나 오래된 지문 때문에 과거 버전의 승인 이력을 지우지는 않습니다.

**정책 문서 유지보수는 직접 편집 예외입니다.**
명시적으로 요청한 `AGENTS.md`, 어댑터, 시작 프롬프트, `README.md`, `docs/`의 정책 텍스트는 프로젝트 초기화나 PLAN 승인 없이 수정합니다.
런타임·스키마·프로젝트 기록 변경은 포함되지 않습니다. 정책 변경이 코드의 강제 조건을 바꾸지도 않습니다.
커밋·push는 요청된 경우에 수행합니다.

[승인 운영](docs/APPROVALS.md)과 [변경 절차](docs/DEVELOPMENT_METHOD.md#change-cycle-and-propagation)를 참고하세요.

## 검증, 차단 사유와 완료 보고

구현·검증·인수·종료는 각각 근거가 필요한 주장입니다.

| 상태 | 의미 |
|---|---|
| `IMPLEMENTED` | 해당 범위가 구현됨 |
| `STATIC_VERIFIED` | 요구한 정적 검증 수준의 근거가 있음 |
| `INTEGRATION_VERIFIED` | 요구한 통합 동작을 검증함 |
| `BROWSER_VERIFIED` | 요구한 브라우저 동작을 확인함 |
| `LIVE_ENV_VERIFIED` | 명시한 실제 환경에서 확인함 |
| `CUSTOMER_ACCEPTED` | 해당 버전에 필요한 최종 고객 인수 요건을 충족함 |
| `CLOSED` | 프로젝트의 해당 종료 기준과 의무를 충족함 |

필요한 검증 수준은 기능별 완료 기준으로 정합니다.
근거에는 검증한 버전·대상 파일, 방법·환경, 기대값·관찰값과 한계를 남깁니다.
미실행·실패·부분 성공·모호함·오래된 결과를 PASS로 바꾸지 않습니다.
변경된 부분과 영향받는 부분을 재검증하고, 영향받지 않은 근거는 적용 가능성을 확인한 뒤 재사용합니다.

미해결 항목은 실제 영향에 맞게 다룹니다.
`G0`는 전체 PLAN/TASK를 막고, `G1`은 지정된 작업·기능·기준을 막습니다. 활성 `G0/G1`은 프로젝트 종료도 막습니다.
`G2`는 조건을 드러낸 채 진행할 수 있는 경고·가정, `G3`는 관찰 항목입니다.
선행 작업 미완료, 충돌하는 점유, 잘못된 기록·승인, 오래된 증거 등의 게이트 실패도 우회하지 않습니다.
관련 없는 작업은 자신의 권한과 게이트가 유효한 동안 진행할 수 있습니다.

기능 완료에는 해당 완료 기준의 적합한 증거가 필요합니다.
프로젝트 종료는 전달·인계·유지보수 준비와 필요한 승인·종료 게이트를 확인하며, PLAN 종료나 배포 성공만으로 대신하지 않습니다.

## 협업과 기존 작업 보존

일반적인 단일 에이전트 작업에는 별도 점유 기록이 필요 없습니다.
여러 작성자가 동시에 작업할 때는 겹치지 않는 경로와 논리적 자원에 claim을 사용하고, 가능한 경우 Git worktree를 분리합니다.
다른 활성 claim의 파일과 출처 미확인 변경은 보존합니다. Claim은 작업 충돌을 조정하며 실행 승인을 부여하지 않습니다.

담당자가 바뀌면 변경 파일·버전, 검증 결과, 한계와 다음 작업을 전달합니다.
별도 결과·리뷰·인계 기록은 릴리스, 감사, 독립 검토, 소유권 이전처럼 필요한 목적에 사용합니다.
공식 결과를 기록하는 흐름에서는 최신 시도가 기준이며, 새 실패를 과거 PASS로 가리지 않습니다.
현재 공식 `result submit`과 `handoff create` 명령은 claim을 요구합니다.
해당 공식 기록이 필요한 단독 작업은 실제 작업 시도 전에 필요한 범위의 claim을 확보할 수 있습니다.
이미 끝낸 작업을 나중에 claim 아래 수행한 것처럼 기록하지 않습니다. 뒤늦게 공식 기록이 필요해지면 기존 이력을 보존하고 [단독 작업의 공식 기록 절차](docs/COLLABORATION.md#formal-records-for-a-single-writer)를 따릅니다.

Push 전에는 설정된 원격 저장소를 fetch하고 양쪽 변경을 보존합니다.
강제·태그 push, 브랜치 삭제, 다른 대상으로의 push, 게시 이력 재작성에는 별도 명시적 권한이 필요합니다.

자세한 기준은 [협업 정책](docs/COLLABORATION.md)에 있습니다.

## 고위험 작업과 보안

다음 다섯 경계에는 암호학적으로 검증되는 인간 서명 승인이 필요합니다.

| 경계 | 예 |
|---|---|
| 운영 배포 | 운영 서비스에 새 버전 배포 |
| 운영 데이터 변경 | 운영 DB 마이그레이션, 데이터 보정 |
| 파괴적 작업 | 운영 자원·데이터 삭제 |
| 비밀·보호된 자격 증명 접근 | 서비스 키나 운영 자격 증명 읽기 |
| 최종 고객 인수 | 특정 결과물 버전의 최종 인수 승인 |

에이전트는 요청서를 준비하고 서명된 결정을 가져와 검사할 수 있습니다.
서명과 보호된 승인 원장 반영은 권한 있는 인간 또는 별도 승인 시스템이 수행하며, 에이전트가 대신하지 않습니다.
인간 서명용 개인키 접근은 에이전트에게 허용되는 실행 능력에 포함되지 않습니다.
한 종류의 승인이 다른 고위험 작업까지 허용하지는 않습니다.

**현재 런타임은 고위험 기능이 포함된 PLAN 자체에도 서명을 추가 요구합니다.**
에이전트는 실행안 준비 단계에서 이 조건과 개별 작업 승인을 함께 설명하고 준비합니다.
일반 로컬 작업의 PLAN에는 이 추가 서명이 필요하지 않습니다.
자세한 내용은 [고위험 PLAN 승인](docs/APPROVALS.md#plans-containing-high-risk-capabilities)을 참고하세요.

하네스는 기록과 실행 조건을 검사하는 도구이며, 프로세스를 격리하는 샌드박스는 아닙니다.
자격 증명과 보호된 승인 자료를 기록·로그·인계 문서에 넣지 않고, 신뢰하지 않는 코드를 특권이나 운영 자격 증명과 함께 실행하지 않습니다.
보호된 실행과 적대적 환경에서의 검토자 분리는 외부 CI·오케스트레이터와 권한 분리가 담당합니다.

긴급 수정도 승인된 PLAN의 TASK와 게이트를 따릅니다.
하네스 기록을 처음부터 다시 만드는 `reset`은 사용자가 하네스 reset 또는 프로젝트를 처음부터 다시 시작하라고 명시적으로 요청한 경우에만 별도 절차로 수행합니다.
먼저 dry run의 삭제 범위와 보존 스냅샷을 보고하고, 미커밋 기록의 유일한 사본이 될 수 있는 로컬 스냅샷과 인간 결정 런타임을 보존합니다.
막힌 게이트를 해결하려고 자동으로 reset하거나 스냅샷을 삭제하지 않습니다.

[보안 정책](docs/SECURITY.md), [서명 승인 절차](docs/APPROVALS.md#protected-authority), [긴급 수정](docs/WORKFLOW.md#hotfixes-and-incidents), [reset 절차](docs/WORKFLOW.md#starting-over)를 참고하세요.

## 저장소와 기록 구조

| 위치 | 역할 |
|---|---|
| `AGENTS.md` · 어댑터 · 시작 프롬프트 | 공통 정책과 에이전트별 시작 지침 |
| `docs/` | 개발 방법, 운영 절차, 보안·협업 기준, 현재 구조와 향후 설계 |
| `scripts/harness.py` | 하네스 명령 진입점 |
| `.harness/tooling/project_harness/` | 런타임과 스키마 |
| `.harness/tooling/tests/` | 하네스 자체 테스트 |
| `.harness/project.json` · `state.json` | 초기화 후 생성되는 프로젝트 설정과 현재 진행 상태 |
| `.harness/sources/` · `artifacts/` | 입력 자료와 버전·파일 근거 |
| `.harness/requirements/` · `features/` | 요구사항, 기능과 완료 기준 |
| `.harness/plans/` · `work-items/` | PLAN과 TASK |
| `.harness/open-items/` · `changes/` | 미해결 사항과 필요한 변경 추적 |
| `.harness/evidence/` · `approvals/` | 검증 관찰과 인간 결정 |
| `.harness/results/` · `reviews/` · `handoffs/` | 필요한 경우 사용하는 공식 결과·리뷰·인계 기록 |
| `.harness/events/` · `baselines/` · `decisions/` | 이벤트, 승인 당시 스냅샷, 서명 요청 자료 |
| `HANDOFF.md` · 보고서 | 사람이 읽는 파생 문서. 원본 기록이나 승인·검증 근거를 대체하지 않음 |

기본 연결은 **출처 → 요구사항 → 기능·완료 기준 → 작업 → 검증 근거**입니다.
실행을 준비할 때 PLAN/TASK를 작성하며, 조사 시작부터 빈 실행 기록을 만들지는 않습니다.
변경·감사 기록은 필요한 범위에서 사용하고, 검증·완료 주장에는 그에 맞는 증거를 갖춥니다.

현재 PLAN/TASK는 Markdown이며 **front matter가 공식 기록**입니다.
본문은 설명을 담고 실행 권한을 부여하지 않습니다. 다른 프로젝트 기록과 상태는 현재 JSON을 사용합니다.
PLAN/TASK의 파생 연결은 `new task --plan`, `plan sync` 등으로 유지하며 수동으로 조작하지 않습니다.
프로젝트 종료의 `approval_dependencies`는 별도의 명시적 목록으로, 에이전트가 실제 PLAN·승인·증거 경로를 작성하고 검증합니다.
현재 `plan sync`는 이 프로젝트 목록을 자동 작성하지 않습니다. [종료 준비 절차](docs/WORKFLOW.md#closure-preparation)를 따릅니다.

Git worktree 간 claim·메일함·인간 결정 마커는 Git 공통 런타임에서 공유됩니다.
보호된 서명 설정과 승인 원장은 저장소 밖에 있습니다.
저장소 파일을 복사해도 이러한 실행 환경의 권한 상태까지 복사되지는 않습니다.
동일 worktree 집합, 같은 경로에서의 결정 마커 복구, 다른 경로로의 이전을 구분해 [결정 복구·이전 절차](docs/APPROVALS.md#checkout-transfer-and-decision-recovery)를 따릅니다.
원래 결정이 그대로 유효한 재시도는 새 승인이 아니며, 저장소 경로 등 결합 조건이 달라지면 대상 환경의 실제 결정이 필요할 수 있습니다.

## 상태 확인과 검사

아래 명령은 에이전트가 요청 범위와 현재 단계에 맞춰 사용합니다.
명령이 제안하는 다음 작업이나 검사 통과 자체는 실행 권한이 아닙니다.

| 명령 | 용도와 시점 |
|---|---|
| `python scripts/harness.py next` | 세션 시작과 현재 범위의 다음 작업 안내 |
| `python scripts/harness.py doctor` | 초기화 후, 환경·승인 권한 변경 시, 고위험 작업 전 진단 |
| `python scripts/harness.py status` | 상세 조사가 필요할 때 전체 상태 확인 |
| `python scripts/harness.py validate --strict` | PLAN 결정·실행 전, 기록 변경 후, 릴리스·공식 인계·결과·push 전 기록 검사 |
| `python scripts/harness.py report decision-package PLAN-0001` | 작성된 범위·지문·사전 점검 결과를 결정안으로 확인 |
| `python scripts/harness.py gate task TASK-0001` | 실제 시작할 TASK의 실행 조건 검사 |
| `python scripts/harness.py report completion` | 기능·프로젝트 완료 조건과 부족한 근거 확인 |

`NEEDS_INIT`는 아직 프로젝트 기록이 없다는 안내입니다.
`NEEDS_PLAN_DETAIL`이면 계획을 보완하고, 실행 요청에서 `NEEDS_PLAN_APPROVAL`이면 준비한 범위에 대한 실제 결정을 받습니다.
`NEEDS_DECISION_APPLIED`는 기록된 결정을 적용하는 단계이며 같은 승인을 다시 묻지 않습니다.
`SCOPE_COMPLETE`에서는 완료를 보고하고, 요청받지 않은 TASK를 추가하지 않습니다.

저장소 검사는 다음과 같이 구분합니다.

| 명령 | 검사 범위 |
|---|---|
| `python scripts/check_repo.py fast` | 존재하는 대상의 Python 컴파일과 프로젝트 기록 strict 검사 |
| `python scripts/check_repo.py full` | 위 검사와 프로젝트 `tests/`의 unittest 검사. 인자를 생략해도 full |
| `python scripts/check_repo.py full --self-test` | 위 검사에 하네스 자체 테스트 추가 |

릴리스·공식 인계·결과·push 전에는 저장소 검사를 수행합니다.
프로젝트에 필요한 통합·브라우저·실환경 검사는 해당 완료 기준에 맞춰 별도로 수행합니다.
테스트나 프로젝트 기록이 없으면 해당 항목이 `SKIPPED`일 수 있으며, 전체 명령의 종료 코드가 0이어도 생략된 검사를 PASS로 보고하지 않습니다.
정책만 편집하는 미초기화 저장소에서는 기록 검증을 명시적으로 건너뛰고 문서 변경과 링크를 확인합니다.

평소에는 `next`를 기준으로 필요한 정책 절과 기록만 읽습니다.
전체 문서 검토가 요청된 경우를 제외하면 README·전체 상태·모든 정책을 반복해서 읽지 않으며, 문맥을 줄일 때도 권한·기존 변경·차단 사유·실패·검증 한계는 보존합니다.

## 현재 지원 범위와 향후 설계

현재 정책과 런타임 사이에 남은 진행 제약이 있습니다. 아래 정책 보완을 런타임 수정 완료로 해석하지 않습니다.

| 진행 제약 | 현재 처리 |
|---|---|
| 과거 증거와 무관한 초안 때문에 strict 실패 | 이력·초안을 보존하고 정확한 차단 사유를 보고합니다. 선택한 범위와 과거 이력을 구분하는 런타임 보완이 필요합니다. |
| 인수·배포 상태의 TASK 실행 및 재작업 복귀 제한 | 해당 상태로 이동하기 전에 실행 경로를 확인합니다. 임의 상태 변경이나 게이트 우회로 진행하지 않습니다. |
| 여러 PLAN의 기능을 합산하는 프로젝트 종료 제한 | 실제 릴리스 목록을 준비하되, 단일 활성 PLAN 조건으로 막히면 종료 불가를 명시합니다. 가상의 완료 TASK를 만들지 않습니다. |
| 고위험 PLAN 서명·공식 단독 기록·종료 목록·체크아웃 이전 | 현재 전제 조건을 충족하는 정책 절차를 사용합니다. 자동화나 모든 경우의 지원을 뜻하지 않습니다. |

8개 항목의 현재 동작, 정책상 처리와 향후 검증 기준은 [진행 차단 항목](docs/RUNTIME_GAPS.md#current-progress-blockers)에 정리되어 있습니다.

| 항목 | 현재 상태 |
|---|---|
| 일반 실행 승인 | 구체적인 범위의 프롬프트 결정을 기록·적용하고 PLAN/TASK 게이트로 검사 |
| 여러 PLAN의 결정 공유 | 명시적인 실행 범위 안에서 단일 수준 PLAN끼리 지원. 개별 적용과 TASK 게이트 필요 |
| 기존 프로젝트 인수·역공학 | 정책과 에이전트 분석 절차로 지원. 전용 자동 인수·문서 변환 명령은 없음 |
| 기록 형식 | PLAN/TASK는 Markdown, 그 밖의 프로젝트 기록은 JSON |
| 부모·자식 PLAN, 카테고리·프로젝트 프로필 | 향후 설계. 현재 `--parent`, `init --profile`, `active_plans`를 사용하지 않음 |
| 모든 기록의 Markdown 전환 | 향후 설계. 현재 `records migrate`나 `project.md`로 운영하지 않음 |

현재 상태는 [런타임 상태와 호환성](docs/RUNTIME_GAPS.md)을 기준으로 확인합니다.
[계층 PLAN](docs/PLAN_HIERARCHY.md)과 [전체 기록 형식 전환](docs/RECORD_FORMAT.md)에 적힌 미래 명령은 현재 기능이나 실행 허가가 아닙니다.
날짜가 붙은 검토 보고서는 당시의 관찰 이력이며, 현재 동작이나 검증 통과를 대신하지 않습니다.
